[Hermes Agent](https://hermes-agent.nousresearch.com) can use any
OpenAI-compatible `/v1/chat/completions` endpoint as a custom provider.

| | |
| --- | --- |
| **Provider** | `custom:camel-stream` |
| **Model** | `deepseek-v4-flash` |
| **Base URL** | `https://stream.camelai.com/v1` |
| **Key** | `CAMEL_API_KEY` |
| **Context window** | 256k input tokens |

<Note>
  Hermes is a third-party agent. Camel Stream provides the model. Review the
  [Hermes security policy](https://github.com/NousResearch/hermes-agent/security)
  before connecting a key.
</Note>

## 1. Install Hermes

```bash Terminal
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
source ~/.zshrc
```

See the [Hermes installation guide](https://hermes-agent.nousresearch.com/docs/getting-started/installation)
if you use bash or install from source.

## 2. Create a Stream key

Generate an API key in [the Stream console](https://stream.camelai.com/console).
It is shown once. Put it in Hermes' env file, not in `config.yaml`.

```bash ~/.hermes/.env
CAMEL_API_KEY=qaml_live_...
```

## 3. Point Hermes at Stream

The fastest path is the built-in wizard, the same one OpenRouter documents:

```bash Terminal
hermes model
```

Choose **Custom endpoint**, then enter:

| Field | Value |
| --- | --- |
| URL | `https://stream.camelai.com/v1` |
| API mode | Chat Completions |
| Key | your `CAMEL_API_KEY` |
| Model | `deepseek-v4-flash` |
| Context length | `262144` |

Or add a named custom provider to `~/.hermes/config.yaml`:

```yaml ~/.hermes/config.yaml
custom_providers:
  - name: camel-stream
    base_url: https://stream.camelai.com/v1
    key_env: CAMEL_API_KEY
    api_mode: chat_completions
    models:
      deepseek-v4-flash:
        context_length: 262144

model:
  provider: custom:camel-stream
  default: deepseek-v4-flash
  context_length: 262144
```

## 4. Start and verify

```bash Terminal
hermes chat --provider custom:camel-stream --model deepseek-v4-flash
```

In a session you can switch with
`/model custom:camel-stream:deepseek-v4-flash`.

```bash Terminal
hermes doctor
```

`hermes doctor` should see the custom provider. If auth fails, confirm
`CAMEL_API_KEY` is in `~/.hermes/.env`.

## Subagents and one stream

<AccordionGroup>
  <Accordion title="Do Hermes subagents work with Stream?">
    Yes. A subagent is just another model request, so nothing breaks. How
    well they work depends on how many streams you have, since each stream
    runs one request at a time.
  </Accordion>
  <Accordion title="What happens when a prompt spawns three subagents on one stream?">
    One request runs and the rest [queue](/stream/queues-and-errors) until a
    slot frees up. Hermes runs subagents in parallel, up to 10 at once on
    current builds, and every session shares your account's streams, so the
    queue builds fast.
  </Accordion>
  <Accordion title="What happens if a request queues for too long?">
    Queued requests wait silently, and Hermes kills any request that stays
    silent past 10 minutes; older builds kill after as little as 90 seconds.
    Each kill loses the request's place in line, so the retry starts over at
    the back of the queue, where it can time out again. After several kills
    in a row Hermes stops retrying and the turn fails. Queue waits only get
    that long under dense parallel work, and raising Hermes' timeouts
    (covered below) should reduce the likelihood of a request getting
    killed.
  </Accordion>
  <Accordion title="How do I set up Hermes for parallel work?">
    There are a few options to get Stream to work well with Hermes. First,
    if your workload involves heavy use of parallel work, we recommend you
    purchase at least 1 additional Stream. Each subscription adds one
    concurrent stream, so subagents run truly in parallel.

    If you prefer to keep 1 stream, we recommend you cap subagents so only
    one runs at a time. Raising Hermes' timeouts can also help queued
    requests survive the wait. The setup below covers both.
  </Accordion>
</AccordionGroup>

To run Hermes on one stream, cap delegation so only one subagent runs at a
time:

```yaml ~/.hermes/config.yaml
delegation:
  max_concurrent_children: 1
  max_spawn_depth: 1
  orchestrator_enabled: false
```

Capping beats disabling subagents outright: subagents do useful work, like
keeping the main agent's context compact, and a cap keeps that. A child
still runs alongside its parent, so some queueing remains and
subagent-heavy prompts run slower than on a multi-stream account.

If requests still get killed, you can also raise Hermes' timeouts so queued
requests outlast the wait:

```bash ~/.hermes/.env
HERMES_API_TIMEOUT=3600
HERMES_API_CALL_STALE_TIMEOUT=3600
HERMES_STREAM_READ_TIMEOUT=3600
HERMES_STREAM_STALE_TIMEOUT=3600
```

This gives every request an hour to clear the queue. It's a backstop rather
than a fix: the queue is just as long, and a genuine outage also looks like
a hang for up to an hour.

<Note>
  Set the timeouts in `.env`, not per provider in `config.yaml`. Hermes
  normalizes named custom providers before some timeout lookups, so
  `request_timeout_seconds` and `stale_timeout_seconds` under
  `custom_providers` may not apply.
</Note>
